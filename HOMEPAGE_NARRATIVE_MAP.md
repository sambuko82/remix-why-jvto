## Homepage Narrative Map

This file fixes the homepage narrative and section jobs for the active frontend.

Active rules:

- Visual grammar stays native to `remix-why-jvto`
- Content logic comes from:
  - local JVTO discussion and strategy
  - `JVTO-Why-JVTO-Next15`
  - `jvto-web`
  - `DB mirror`
- Homepage must feel like one system, not a stack of unrelated modules
- If a remix slot can hold the content, reuse it
- If a section is too fragmented, compress or merge it before creating anything new

### Final Homepage Sequence

1. `Hero`
   - Job: establish operator identity and trust hook fast
   - Core message:
     - private volcano routes
     - East Java
     - police-led context
     - verify before payment
   - H1 stays calm and poster-like

2. `Differentiators`
   - Job: compress the three reasons JVTO is different
   - Required cues:
     - police-led route handling
     - doctor-backed Ijen screening
     - proof before payment

3. `Founder Spotlight`
   - Job: human authority layer
   - Explain why JVTO feels operationally different, not just marketed differently

4. `Destinations`
   - Job: place desire and operational footprint
   - Image-led, fast to scan

5. `Featured Tours`
   - Job: route-family and package-entry layer
   - Homepage should shortlist, not behave like a full browser

6. `Operational Transparency`
   - Job: merge three homepage needs into one efficient slot:
     - why JVTO
     - prepare & book
     - live volcano context
   - This section absorbs the old standalone MAGMA and support interruptions

7. `Final Verify CTA`
   - Job: give one last proof path before footer

8. `Footer`
   - Job: clarify route, trust, support, and external proof ownership

### Removed From Homepage

These stay available on the site but should not remain as standalone homepage interruptions:

- standalone volcano status block
- standalone Ijen health block
- standalone reviews block
- standalone FAQ block
- standalone crew block
- homepage contact block

### Why This Structure

The redesign is not about appearance alone.
It exists to solve the old homepage problem:

- trust was scattered
- support was fragmented
- route discovery was interrupted
- proof looked like separate widgets instead of decision support

The homepage should now move in one direction:

1. understand the operator
2. understand why the operator is different
3. see the destinations and route families
4. understand where support and live context live
5. verify before payment if needed
